# Guardian storage schema

Current schema: **19**. `GuardianSchema` and `SchemaMigrator` in `common` are authoritative for migrations. Startup upgrades supported older databases; newer unsupported schemas are refused. Back up before upgrading and retain the backup for downgrade.

The `ex_` table prefix preserves the native ExProtect format lineage. It is not a CoreProtect `co_` schema or an automatic importer.

- Metadata/migration/sequence tables track format, clean shutdown and portable identities.
- Mapping tables store dimensions, resources, block-state properties and actors.
- Block history stores event identity, time, actor, position, before/after state and payload, action/cause and rollback state.
- Container history stores correlated immutable slot changes with item counts and persistent component payloads. Logical owner indexes support checking history omitted by filters.
- Item recovery tables retain operation records, entries, owner/transaction claims, unresolved protection and complete saved images/reconciliation decisions. These do not expose item apply.

Block rollback state values are `0 ACTIVE`, `1 ROLLED_BACK`, `2 PENDING`, `3 RESTORE_PENDING`. Pending rows retain interrupted reconciliation work; queries excluding rolled-back rows still retain pending rows. Newly claimed untouched active rows can be released after permission revocation, while older pending recovery state is preserved.

Schema 7 introduced item journals/claims, 8 added owner history indexing, 9 added durable unresolved protection and 10 added complete owner images and reconciliation acknowledgement. Existing block payloads and older supported item encodings remain readable. Do not manually delete recovery tables/claims to bypass refusal.

Stop the server before a simple database-file backup. Default SQLite location is `guardian/guardian.sqlite` under the server directory. Backend selection does not migrate history to another database.

Schema 11 adds `ex_player_activity`: unique event UUID, timestamp, player UUID, immutable event-time name, CHAT/LOGIN/LOGOUT kind and nullable plain chat text. Kind/time and UUID/time indexes support bounded lookups. Retries ignore an existing event UUID; activity writes share the audit batch transaction. These records do not participate in block/item rollback.

Schema 12 adds derived `ex_container_item` rows keyed by transaction UUID and resource ID, with a resource/transaction index. It indexes all recorded nonempty before/after stack identities, not display names or component contents. A keyset backfill closes each read cursor before batch writes and preserves existing payload bytes. Resource conditions use EXISTS/NOT EXISTS before limit/offset, avoiding duplicate transaction rows.

Schema 13 marks the directional restore journal contract without rewriting audit payloads. Restore uses `ROLLED_BACK -> RESTORE_PENDING -> ACTIVE` and chronological ascending replay. Rollback uses `ACTIVE -> PENDING -> ROLLED_BACK` and descending replay. Explicit state predicates run before paging. Ordinary rollback excludes restore-pending work; restore excludes active and rollback-pending work. Untouched newly claimed rows can return to their original state, while pre-existing unresolved pending rows retain their direction. A retry finalizes a matching target or applies from a matching source; a conflict is not overwritten. Database flags and Minecraft chunk saves are separate persistence boundaries. A pending marker permits conservative matching-state reconciliation, not an atomic world/database crash guarantee. Back up before upgrade; older builds refuse schema 13.

Schema 14 marks purge completeness semantics. Installing/upgrading does not delete history. A successful confirmed block/item purge writes a monotonic `ex_meta.history_purged_before` cutoff in the same transaction as the selected deletions. Item guards report INCOMPLETE_HISTORY for selected transactions strictly older than that floor, including late reinsertions. Journal preparation also checks this guard. Activity-only purge does not advance the floor. Since alpha.74, entity/frame and fluid records also participate in confirmed purge; deleting only these categories does not advance the floor either. This is a purge-policy change, with no new schema migration. Recovery journals still protect block/item history and are never purged.

Purge selects fixed keys for at most 1,000 records across block, container and activity tables. It rechecks timestamps and recovery protection under the backend lock before deleting. Container location, logical owner and resource indexes are deleted with their parent row. Block PENDING/RESTORE_PENDING rows and their positions are protected. Any retained item-journal/protection/claim/image data conservatively protects all block/container rows. Journal tables, maps, sequences and recent data remain. There is no automatic compaction or identity reset. Pre-commit cancellation rolls the transaction back, including index changes and the floor; cancellation after commit cannot restore deleted history. Retain a pre-upgrade database backup for downgrade to a schema-13 build.

Schema 15 admits COMMAND in `ex_player_activity.kind`, using the existing unique event UUID and kind/time/player indexes. Bounded command text is stored only after capture policy redaction; it uses ActionType.COMMAND (51). Commands are queried independently from chat and session kinds. Standard activity purge includes old command records in its fixed batch. No old payloads are rewritten by the empty marker migration, and older builds refuse schema 15. Argument-capture changes do not rewrite stored records. Signed command/chat materials and transport metadata are not persisted by this feature.

Schema 16 adds `ex_entity`: unique event UUID, timestamp, nullable actor-map reference, dimension ID, block coordinates, target UUID/type ID, DEATH/NAME_CHANGE kind, bounded nullable plain before/after custom names and nullable registry damage type. Time/event, target/time, location/time and actor/time indexes support filtered searches. Query predicates run before stable time/event-UUID paging. Duplicate event IDs are ignored inside the shared batch transaction. No entity NBT, inventories, live objects or signed transport data are stored. The migration preserves existing history and journals; older builds refuse schema 16. At introduction these rows were excluded from purge; alpha.74 includes them in confirmed purge. They do not participate in rollback or item completeness guards.

Schema 17 adds nullable `parent_uuid` and `partner_uuid` columns to `ex_entity` and admits TAME/BREED kinds. Old entity rows retain null parent fields and their original payloads. TAME uses the verified owner player as actor and has no parent/damage fields. BREED targets the inserted offspring, requires two distinct parent UUIDs different from the child, and stores the one available vanilla breeding credit or unknown actor. Parent fields are identity metadata, not rollback state or parent-search filters. Existing entity lookup predicates, pagination, duplicate suppression are unchanged. The original purge exclusion was lifted in alpha.74. Action codes are 34 (tame) and 35 (breed). Older builds refuse schema 17; keep the pre-upgrade backup.

Schema 18 adds `ex_fluid` for read-only bucket history: unique event UUID, timestamp, player actor-map reference, dimension/coordinates, PLACE/REMOVE kind, before/after registered fluid IDs, source flags and host block IDs. Source/identity changes are required; placement needs a persistent after-fluid and removal needs a nonempty before-fluid and empty after-fluid. Time/event, actor/time and spatial/time indexes support bounded queries. Actor/resource/time/spatial/action predicates precede stable time/event UUID paging. Duplicate events are ignored in the shared batch transaction. No mutable world objects, block-entity payloads or full fluid simulation are stored. Fluid events do not enter block/item rollback journals. Alpha.74 includes them in confirmed purge without changing their stored format. Existing histories are preserved and older builds refuse schema 18; retain a pre-upgrade backup.

Schema 20 rebuilds `ex_fluid` transactionally with nullable actor references (the existing unknown-actor convention) and nullable `before_amount`/`after_amount` columns, preserving event IDs, timestamps, actor references and all earlier payload fields. Historical amounts remain null. New immutable fluid snapshots record 0 for empty and 1..8 for present fluid. FLOW and FORM kinds use action codes 38/39. Actor/resource/action predicates still precede pagination, and resource filters also accept host block IDs. Existing purge includes these rows without altering its shared cap or item recovery semantics. Source traces are bounded runtime state, not database ownership claims; restart starts without attribution. Older builds refuse schema 20. Back up before upgrading.

Schema 19 adds nullable `frame_before` and `frame_after` BLOBs to `ex_entity`, with FRAME_PLACE/FRAME_REMOVE/FRAME_CHANGE kinds (action codes 60/61/62). A bounded GFR1 frame codec stores rotation 0..7 and an empty or count-one immutable item snapshot, retaining the existing registry/Data Component-aware opaque item payload up to 1 MiB. Placement has only an after snapshot, removal only a before snapshot, and display changes require unequal before/after values. BLOB reads use column indexes for JDBC compatibility. Existing event rows remain null in both new columns and retain their meanings; older builds refuse schema 19. Frame records use the same actor/type/target/time/spatial queries and remain outside container transactions and rollback. Alpha.74 includes these entity rows and their frame payloads in confirmed purge. Retain a pre-upgrade database backup for downgrade.
